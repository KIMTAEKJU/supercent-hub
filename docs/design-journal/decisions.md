# 기술 의사결정 모음

> 설계 과정에서 명시적으로 "다른 대안과 비교하여" 선택된 주요 기술 결정 7건을 정리했습니다. 각 결정은 프로젝트의 특정 제약(비용/성능/심사 마찰)을 해결하기 위한 것입니다.

---

**supercent-study** 프로젝트 전반에서 내린 주요 기술 의사결정 사항을 배경, 대안, 채택 이유를 중심으로 정리해 드립니다.

### 1. Anthropic API BYOK 대신 Claude Code Routines 채택
*   **배경**: 이전 단계인 AdSpec AI 개발 및 테스트 과정에서 **500달러(약 70만 원) 규모의 API 비용이 폭주**하는 트라우마를 겪었습니다. VPP 기획안은 구조상 AdSpec보다 15배 더 무거운 워크로드(5 페르소나 병렬 시뮬레이션)를 가져 비용 리스크가 감당 불가능한 수준이었습니다.
*   **대안**: 사용자 본인의 API 키를 입력받는 BYOK(Bring Your Own Key) 방식, 혹은 AI 없이 스크립트로만 작동하는 FSM 시뮬레이션.
*   **채택 이유**: Claude Code Routines(2026.04.14 출시)는 Anthropic의 클라우드 인프라에서 실행되는 **정액제(Max 플랜 기준 15 runs/day)** 기반 자동화 도구입니다. 이를 백엔드로 활용하면 추가 API 호출 비용 없이 **비용 리스크를 0으로 통제**하면서도, 단순 챗봇은 할 수 없는 **bash 실행, Git 커밋, 멀티미디어 파이프라인 오케스트레이션** 역량을 증명할 수 있습니다.

### 2. Vercel KV(Upstash Redis)를 상태 메시지 버스로 채택
*   **배경**: Claude Code Routines는 호출 즉시 세션 ID만 반환하고 비동기로 작업을 시작하는 **fire-and-forget(실행 후 망각)** 모델입니다. 따라서 웹 UI는 Routine이 현재 어느 단계(해석/생성/배포 등)에 있는지 알 방법이 없었습니다.
*   **대안**: 비공식 상태 폴링 API 탐색, 혹은 Routine 내부에서 웹 앱으로 역으로 Webhook을 쏘는 방식.
*   **채택 이유**: 웹 앱과 비동기 Routine이 공통으로 접근할 수 있는 **유일한 상태 채널(Message Bus)**로 Vercel KV를 정의했습니다. Routine이 각 단계가 끝날 때마다 KV에 상태를 업데이트하고, 웹 UI가 이를 조회함으로써 **에이전트와 UI 간의 상태 동기화**를 달성했습니다.

### 3. 구조화된 4필드 요청 폼 강제
*   **배경**: 사내 구성원들의 도구 요청은 대개 Slack 등에서 모호한 자연어로 이루어져 휘발되거나 중복되는 경우가 많았습니다.
*   **채택 이유**: **[문제점 / 현재 방식 / 기대 결과 / 예시 입출력]**의 4개 필드를 강제함으로써, 생성 엔진인 Routine이 추가 핑퐁 없이도 **즉시 프로토타입 코드를 생성할 수 있는 구조화된 데이터**를 확보하기 위함입니다. 이는 "단순한 생성"을 넘어 "데이터 레이어 기반의 의사결정"이라는 슈퍼센트의 기조와 정합합니다.

### 4. Fire-and-forget + 3초 폴링 + Vercel READY 이중 확인
*   **배경**: Routine API는 비동기라 응답을 주지 않고, Vercel 배포 훅(Deploy Hook)은 호출 즉시 URL을 반환하지만 **실제 배포 완료까지는 1~2분의 시차**가 발생합니다.
*   **채택 이유**: 
    *   **Fire-and-forget**: Routine API의 고유한 기술적 특성을 수용한 결과입니다.
    *   **3초 폴링**: KV 쿼터(Quota) 소진을 방어하면서도 사용자에게 실시간 진행 상황(5단계 바)을 시각화하기 위한 최적의 주기입니다.
    *   **READY 이중 확인**: Routine이 배포를 완료했다고 보고해도 Vercel URL이 아직 404인 경우가 생기므로, 최종 단계에서 실제 URL의 활성화 여부를 한 번 더 확인하여 **"작동하지 않는 프로토타입 링크"를 제공하는 실수를 차단**합니다.

### 5. `claude/prototype-*` 브랜치 접두사 강제
*   **배경**: 클라우드 기반 AI 에이전트(Claude Code Routine)는 보안 정책상 Git 작업 권한에 제약이 있습니다.
*   **채택 이유**: 기본 설정상 Routine은 **`claude/` 접두사가 붙은 브랜치에만 자동 push가 가능**합니다. 이 기술적 제약을 설계에 미리 반영하여 자동 배포 파이프라인의 **실패 리스크를 사전 차단**하기 위해 네이밍 규칙을 고정했습니다.

### 6. 생성 프로토타입의 "Input → AI 분석 → Result" 패턴 한정
*   **배경**: AI가 실시간으로 복잡한 풀스택 코드를 생성하는 방식은 런타임 실패율이 20~60%에 달해 매우 위험했습니다.
*   **채택 이유**: 제출 마감(4/23)까지의 촉박한 일정과 성공 확률을 고려하여, 생성되는 도구의 범위를 **단일 페이지 기반의 분석형 도구**로 한정했습니다. 복잡한 CRUD나 DB 연동 없이 **"입력값을 받아 AI가 분석 결과를 보여주는" 명확한 템플릿**만 생성하게 함으로써 생성 품질의 일관성과 시스템의 완결성을 확보했습니다.
